React와 Spring Boot로 구조를 나누면 프론트엔드와 백엔드의 역할이 명확해질 것이라고 생각했습니다.

화면은 React가 담당하고, 데이터와 업무 처리는 Spring Boot API가 담당하면 된다는 설명은 단순합니다. 하지만 실제 업무 화면을 나누기 시작하니 어디까지가 화면의 책임이고 어디부터가 서버의 책임인지 애매한 지점이 계속 나타났습니다.

## 데이터를 보여주는 것과 업무를 판단하는 것은 달랐습니다

화면은 사용자의 입력과 상태를 빠르게 표현해야 합니다. 입력값 형식이나 필수 항목을 확인하고, 로딩과 오류 상태를 보여주며, 이전 화면에서 이어진 흐름을 유지합니다.

하지만 화면에서 확인했다고 업무 조건까지 신뢰할 수는 없었습니다.

계좌 상태, 상품 조건, 거래 가능 여부, 권한처럼 실제 처리 결과를 바꾸는 판단은 서버에서 다시 확인해야 했습니다. 전자서명이 포함된 업무라면 사용자가 확인한 데이터와 서버가 처리할 요청이 같은지도 검증해야 했습니다.

이번 프로젝트에서는 사용자 경험을 위한 검증과 신뢰 가능한 업무 검증을 구분했습니다.

- 화면은 빠른 피드백과 입력 편의를 담당합니다.
- API는 업무 가능 여부와 요청 데이터의 정합성을 검증합니다.
- 원장이나 코어 서비스의 응답은 채널 API가 화면에서 사용할 수 있는 형태로 정리합니다.

같은 조건을 프론트엔드와 백엔드에 무작정 중복하는 것이 아니라, 각 검증이 필요한 이유를 구분하려고 했습니다.

## API는 원장 응답을 그대로 전달하지 않았습니다

기존 업무를 API로 분리할 때 원장 응답을 그대로 JSON으로 바꾸면 빠르게 개발할 수 있습니다.

하지만 원장 필드와 메시지는 내부 처리 기준에 가깝습니다. 화면이 원장 구조를 직접 알게 되면 필드 변경의 영향이 프론트엔드까지 이어지고, 화면마다 같은 해석 로직이 반복될 수 있습니다.

그래서 API는 단순한 전달 통로보다 채널 서비스의 경계 역할을 맡도록 했습니다.

화면에 필요한 데이터만 응답하고, 공통 응답과 오류 형식을 맞추며, 기술적인 메시지는 고객이 이해할 수 있는 표현으로 변환합니다. 다국어 지원을 고려해 화면에 노출되는 문구를 비즈니스 코드에 직접 넣지 않는 기준도 함께 잡았습니다.

## 분리된 구조일수록 공통 기준이 필요했습니다

프론트엔드와 백엔드를 분리하면 각 영역이 독립적으로 개발하기 쉬워집니다. 반대로 기준이 없으면 서로 다른 방식도 빠르게 늘어날 수 있습니다.

API의 성공·실패 형식, 인증 정보 전달 방식, 로딩과 오류 표현, 날짜와 금액 형식, 화면 이동과 로그인 복귀 흐름을 먼저 맞췄습니다. Swagger는 개발 중 API를 확인하는 데 사용하고, 테스트로 검증된 명세는 REST Docs로 남기는 방식도 함께 준비했습니다.

중요한 것은 모든 규칙을 처음부터 크게 만드는 일이 아니었습니다. 여러 업무에서 반복될 가능성이 높은 기준부터 공통화하고, 업무 특성에 따른 차이는 도메인 안에 남기는 것이 현실적이었습니다.

## 역할은 나누되 경험은 나누지 않았습니다

React와 Spring Boot로 구조를 분리하는 목적은 기술 영역을 서로 떼어놓는 데 있지 않았습니다.

화면은 변경과 표현에 유연해지고, 서버는 업무 규칙과 검증을 신뢰할 수 있게 만드는 것이 목적이었습니다. 앱까지 포함된 WebView 서비스라면 앱의 네이티브 기능과 화면 이동도 같은 흐름 안에서 이어져야 했습니다.

프론트엔드와 백엔드의 책임은 분리되어야 합니다. 하지만 고객은 그 경계를 구분하지 않습니다. 각 영역의 기준을 분명하게 만드는 일은 결국 하나의 자연스러운 고객 경험을 만들기 위한 과정이라고 생각합니다.
