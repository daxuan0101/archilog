공통 SVG 아이콘을 여러 웹서비스에서 사용하려다가 `mask-image`의 교차 출처 문제를 확인했습니다.

처음에는 CSS 속성이나 이미지 경로를 고치면 되는 화면 문제라고 생각했습니다. 하지만 리소스 서버와 화면의 출처가 달라지자, 아이콘 하나를 보여주는 일에도 서버의 응답 정책이 필요했습니다.

작은 UI 문제처럼 보였지만 실제 질문은 달랐습니다. 이 정적 자산을 누가 사용할 수 있게 할 것인지 먼저 정해야 했습니다.

## mask-image는 주소만 맞는다고 끝나지 않았습니다

`mask-image`는 SVG의 모양을 마스크로 사용하고 색상은 CSS에서 바꿀 수 있어 공통 아이콘을 표현하기에 편리했습니다. 문제는 다른 출처의 SVG를 가져오는 순간 브라우저의 교차 출처 확인이 함께 적용된다는 점이었습니다.

마스크 리소스를 정상적으로 가져오지 못하면 브라우저는 해당 마스크를 표시할 수 없습니다. 화면에서는 아이콘이 사라진 것처럼 보이지만, 원인은 디자인 자산 자체보다 리소스를 제공하는 서버의 응답 헤더에 있을 수 있었습니다.

그래서 CSS와 URL만 보지 않고 세 가지를 함께 확인했습니다.

- 화면과 정적 자산 서버의 출처가 같은가
- 실제 응답에 `Access-Control-Allow-Origin`이 있는가
- 브라우저가 보낸 `Origin`과 서버가 허용한 값이 맞는가

## 여러 도메인을 한 줄에 넣을 수는 없었습니다

처음에는 사용하는 웹 도메인을 응답 헤더에 모두 나열하면 될 것처럼 보였습니다. 하지만 `Access-Control-Allow-Origin`은 여러 출처를 쉼표로 나열하는 형식이 아닙니다. `*.example.com`처럼 하위 도메인을 패턴으로 적는 방식도 허용 목록으로 동작하지 않습니다.

응답은 요청에 맞는 하나의 출처를 반환하거나, 자격 증명이 필요 없는 공개 리소스라면 `*`를 사용할 수 있습니다. 이 차이를 모르고 도메인 목록만 늘리면 설정은 있어 보여도 브라우저에서는 계속 거절될 수 있습니다.

여기서 기준을 두 가지로 나누었습니다.

- 누구나 사용해도 되는 공용 SVG와 이미지라면 여러 화면에서 재사용할 수 있도록 공개 범위를 정합니다.
- 인증 정보나 사용자별 데이터와 연결된 리소스라면 허용한 출처를 확인한 뒤 요청의 출처와 일치하는 값을 응답합니다.

같은 조직의 도메인인지보다, 그 리소스가 어떤 데이터를 담고 어떤 방식으로 요청되는지가 더 중요한 기준이었습니다.

## 설정 변경보다 확인 순서가 중요했습니다

서버 설정을 바꾸는 것만으로 작업이 끝나는 것도 아니었습니다. 운영 중인 웹서버에서는 설정 문법을 먼저 검증하고, 정상일 때만 반영한 뒤 실제 응답을 확인해야 했습니다.

확인 순서는 단순하게 정리했습니다.

1. 변경 전에 기존 설정과 적용 대상을 확인합니다.
2. 응답 헤더 정책을 추가한 뒤 문법 검증을 통과시킵니다.
3. 설정을 반영하고 `Origin` 헤더를 넣은 요청으로 응답을 확인합니다.
4. 마지막으로 실제 화면에서 마스크가 표시되는지 확인합니다.

명령이 성공했다는 사실과 브라우저가 리소스를 사용할 수 있다는 사실은 같지 않았습니다. 응답 헤더와 화면 결과를 모두 확인해야 적용이 끝났다고 볼 수 있었습니다.

## 정적 자산도 플랫폼의 계약이었습니다

이번 문제를 확인하면서 정적 자산 서버를 단순한 파일 보관 장소로 보기 어려워졌습니다.

공통 아이콘을 여러 서비스가 사용하려면 URL 규칙뿐 아니라 캐시, 콘텐츠 유형, 교차 출처 정책과 변경 절차도 함께 관리해야 합니다. 디자인 시스템에서 만든 자산이 실제 서비스에서 재사용되려면 이런 운영 기준까지 이어져야 했습니다.

CSS 아이콘 하나가 보이지 않는 문제에서 시작했지만, 결국 정리해야 했던 것은 자산의 공개 범위와 검증 방식이었습니다. 화면에서 재사용할 수 있는 자산은 파일만 공통으로 두는 것이 아니라, 여러 채널이 예측 가능한 방식으로 가져갈 수 있게 제공해야 한다고 생각합니다.
