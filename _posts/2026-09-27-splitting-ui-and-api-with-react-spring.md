## 화면과 API를 나누면 끝이라고 생각했습니다

React와 Spring Boot로 구조를 나누면 프론트엔드와 백엔드의 역할이 명확해질 것이라고 생각했습니다.

화면은 React가 담당하고, 데이터와 업무 처리는 Spring Boot API가 담당하면 된다는 설명은 단순합니다. 하지만 실제 업무 화면을 나누기 시작하니 어디까지가 화면의 책임이고 어디부터가 서버의 책임인지 애매한 지점이 계속 나타났습니다.

역할을 정리한 뒤에는 또 다른 질문이 남았습니다. 코드는 나누었는데, 변경하고 빌드하고 배포하는 단위도 실제로 나뉘어 있는가 하는 문제였습니다.

### 데이터를 보여주는 것과 업무를 판단하는 것은 달랐습니다

화면은 사용자의 입력과 상태를 빠르게 표현해야 합니다. 입력값 형식이나 필수 항목을 확인하고, 로딩과 오류 상태를 보여주며, 이전 화면에서 이어진 흐름을 유지합니다.

하지만 화면에서 확인했다고 업무 조건까지 신뢰할 수는 없었습니다.

계좌 상태, 상품 조건, 거래 가능 여부, 권한처럼 실제 처리 결과를 바꾸는 판단은 서버에서 다시 확인해야 했습니다. 전자서명이 포함된 업무라면 사용자가 확인한 데이터와 서버가 처리할 요청이 같은지도 검증해야 했습니다.

이번 프로젝트에서는 사용자 경험을 위한 검증과 신뢰 가능한 업무 검증을 구분했습니다.

- 화면은 빠른 피드백과 입력 편의를 담당합니다.
- API는 업무 가능 여부와 요청 데이터의 정합성을 검증합니다.
- 원장이나 코어 서비스의 응답은 채널 API가 화면에서 사용할 수 있는 형태로 정리합니다.

같은 조건을 프론트엔드와 백엔드에 무작정 중복하는 것이 아니라, 각 검증이 필요한 이유를 구분하려고 했습니다.

### API는 원장 응답을 그대로 전달하지 않았습니다

기존 업무를 API로 분리할 때 원장 응답을 그대로 JSON으로 바꾸면 빠르게 개발할 수 있습니다.

하지만 원장 필드와 메시지는 내부 처리 기준에 가깝습니다. 화면이 원장 구조를 직접 알게 되면 필드 변경의 영향이 프론트엔드까지 이어지고, 화면마다 같은 해석 로직이 반복될 수 있습니다.

그래서 API는 단순한 전달 통로보다 채널 서비스의 경계 역할을 맡도록 했습니다.

화면에 필요한 데이터만 응답하고, 공통 응답과 오류 형식을 맞추며, 기술적인 메시지는 고객이 이해할 수 있는 표현으로 변환합니다. 다국어 지원을 고려해 화면에 노출되는 문구를 비즈니스 코드에 직접 넣지 않는 기준도 함께 잡았습니다.

### 분리된 구조일수록 공통 기준이 필요했습니다

프론트엔드와 백엔드를 분리하면 각 영역이 독립적으로 개발하기 쉬워집니다. 반대로 기준이 없으면 서로 다른 방식도 빠르게 늘어날 수 있습니다.

API의 성공·실패 형식, 인증 정보 전달 방식, 로딩과 오류 표현, 날짜와 금액 형식, 화면 이동과 로그인 복귀 흐름을 먼저 맞췄습니다. Swagger는 개발 중 API를 확인하는 데 사용하고, 테스트로 검증된 명세는 REST Docs로 남기는 방식도 함께 준비했습니다.

중요한 것은 모든 규칙을 처음부터 크게 만드는 일이 아니었습니다. 여러 업무에서 반복될 가능성이 높은 기준부터 공통화하고, 업무 특성에 따른 차이는 도메인 안에 남기는 것이 현실적이었습니다.

## 책임은 분리됐지만 변경 단위는 여전히 묶여 있었습니다

화면과 API의 책임을 정리하고 나니, 이번에는 변경을 어떤 단위로 관리할지 고민하게 되었습니다.

화면만 수정했는데 여러 애플리케이션을 함께 빌드해야 하거나, 한 서비스의 변경을 다른 서비스와 같은 릴리즈에 맞춰야 한다면 코드의 분리가 운영의 독립성으로 이어졌다고 보기는 어려웠습니다.

반대로 저장소를 나눈다고 이 문제가 저절로 해결되는 것도 아니었습니다. 저장소가 달라도 API 변경 때마다 함께 배포해야 한다면 두 영역의 변경은 여전히 연결되어 있습니다.

그래서 저장소를 몇 개로 나눌지보다, 무엇을 독립적으로 바꿀 수 있어야 하는지부터 다시 확인할 필요가 있었습니다.

## 무엇을 독립적으로 바꿀 수 있어야 하는가

프론트엔드, 게이트웨이, 업무 API는 모두 같은 서비스 흐름에 참여하지만 변경하는 이유와 주기가 반드시 같지는 않습니다.

화면의 문구나 배치를 바꾸는 일, 요청을 연결하는 방식을 바꾸는 일, 업무 규칙을 바꾸는 일은 영향 범위가 다릅니다. 각 변경에 어떤 검증이 필요하고 어떤 애플리케이션을 다시 배포해야 하는지 설명할 수 있어야 했습니다.

이때 독립 배포를 모든 변경에서 단독으로 배포할 수 있다는 뜻으로 보지는 않았습니다. API 계약이 달라지는 변경은 호환되는 조합과 적용 순서를 함께 확인해야 합니다. 화면이 먼저 바뀌어도 되는지, 서버가 기존 요청을 계속 지원할 수 있는지에 따라 배포 계획도 달라집니다.

독립성의 기준은 경계를 그어 놓았는지가 아니라, 변경의 영향을 확인하고 필요한 범위만 안전하게 내보낼 수 있는지에 가까웠습니다.

## 멀티모듈과 저장소의 역할을 구분했습니다

여러 애플리케이션이 포함된 멀티모듈 구조를 다루면서는 모듈, 저장소, 배포 단위를 같은 의미로 취급하지 않는 것이 중요했습니다.

함께 변경되는 코드와 공통 의존성을 한 구조 안에서 관리하는 일에는 멀티모듈이 도움이 됩니다. 하지만 공통 코드를 묶었다고 모든 애플리케이션이 하나의 배포물이 되어야 하는 것은 아닙니다. 라이브러리로 사용하는 모듈과 실제 실행되는 애플리케이션을 구분하고, 서비스별로 필요한 빌드 대상과 산출물을 식별할 수 있어야 했습니다.

프론트엔드와 백엔드를 별도 저장소로 관리할지도 같은 관점에서 보았습니다. 변경 주기와 검수 책임, 릴리즈 흐름을 각각 관리할 필요가 있는지가 판단 기준이었습니다. 언어와 도구가 다르다는 사실만으로 저장소 분리가 반드시 필요한 것은 아니었습니다.

공통 모듈을 바꿀 때에는 이를 사용하는 애플리케이션의 영향 범위를 함께 확인해야 합니다. 서비스별 빌드가 가능하다는 사실만으로 공통 코드의 변경 영향까지 사라지지는 않기 때문입니다.

결국 저장소는 소스와 협업의 경계이고, 모듈은 코드와 의존성의 경계이며, 배포물은 운영에 반영하는 단위였습니다. 이 관계가 명확해야 어떤 변경이 어느 서비스의 배포로 이어지는지 추적할 수 있었습니다.

## 릴리즈 버전은 운영과의 약속이었습니다

개발 브랜치는 계속 바뀝니다. 같은 브랜치 이름이라도 어느 시점의 코드를 빌드했는지에 따라 결과가 달라질 수 있습니다. 그래서 브랜치 이름만으로 운영에 반영할 대상을 설명하기에는 부족했습니다.

사내 이행 절차 안에서는 검수한 코드와 빌드 산출물, 운영 반영 대상을 이어서 확인할 수 있어야 했습니다. 버전은 그 연결을 설명하는 약속이었습니다.

- 어떤 소스 변경을 기준으로 빌드했는가
- 어떤 애플리케이션의 산출물이며 어떤 릴리즈에 포함되는가
- 검수한 산출물과 실제 반영할 산출물이 같은가
- 함께 사용하는 화면과 API의 버전 조합은 호환되는가
- 문제가 생겼을 때 어떤 이전 산출물로 돌아갈 수 있는가

재현 가능한 배포를 위해서는 버전 이름을 붙이는 것에서 한 걸음 더 나아가야 했습니다. 소스 기준점뿐 아니라 의존성과 빌드 환경을 추적하고, 검증한 산출물을 보관해 이행 대상과 연결할 필요가 있었습니다.

같은 소스로 다시 빌드하는 일과 이미 검증한 산출물을 다시 배포하는 일도 구분해야 합니다. 운영 반영 시점에 새로 만들어진 파일이라면 앞서 검수한 대상과 같은지 다시 확인해야 하기 때문입니다.

중요한 것은 특정 브랜치 규칙이나 배포 도구를 선택하는 일보다, 개발과 운영이 같은 버전과 같은 산출물을 가리키도록 만드는 일이었습니다.

## 역할의 분리는 운영 방식까지 이어져야 했습니다

React와 Spring Boot로 구조를 분리하는 목적은 화면은 React로, 서버는 Spring Boot로 만든다는 설명에 머물지 않았습니다.

화면은 표현과 변경에 유연해지고, 서버는 인증과 업무 검증을 신뢰할 수 있게 맡아야 했습니다. 그 책임을 유지하면서 각 영역을 안전하게 바꾸려면 빌드, 검수, 버전, 배포의 기준도 함께 맞아야 했습니다.

고객은 프론트엔드와 백엔드의 경계를 구분하지 않습니다. 앱까지 포함된 WebView 서비스라면 로그인 복귀와 화면 이동도 하나의 흐름으로 이어져야 합니다. 내부의 분리가 고객 경험의 단절로 이어지지 않도록 연결 지점을 확인하는 일은 여전히 필요했습니다.

## 좋은 분리는 변경의 영향을 예측할 수 있게 합니다

처음에는 화면과 API의 책임을 나누는 데 집중했습니다. 이후에는 그 경계가 소스 관리와 빌드, 운영 반영까지 이어지는지 살펴보게 되었습니다.

좋은 분리는 경계를 많이 만드는 일이 아니라는 생각이 들었습니다. 어떤 코드를 바꾸면 무엇을 확인해야 하고, 어느 산출물을 배포해야 하며, 문제가 생기면 어디로 돌아가야 하는지 설명할 수 있게 만드는 일에 가까웠습니다.

React와 Spring Boot를 나눈 뒤 달라진 것은 기술 구조만이 아니었습니다. 변경을 준비하고 운영에 전달하는 기준도 함께 정리해야 했습니다.
